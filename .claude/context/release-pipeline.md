# Release pipeline: vl-release, CI, packaging, publication

Releases use **vl-release** (`vlr`, installed from `apt.valkyrianlabs.com` as `vl-release`; source at
`/srv/vl-release`). `release.toml` is the contract; `vlr help config|staging|ci` are the offline references and the
`/vl-release` skill (`.claude/skills/vl-release/{SKILL,PROJECT}.md`, regenerated by `vlr install-skill` /
`vlr install-local-skill`) is the working procedure. The in-repo `tools.release` (AI changelog pipeline, own
build/publish code, success ledger) was removed in 1.8.0.

## Versions

`VERSION` is canonical; `meson.build` (meson) and `web/package.json` (package_json) are managed targets. Never edit
them by hand: `vlr version check | bump patch|minor|major | set X.Y.Z`. `debian/changelog` is **not** a version
target: it is published history, extended only by `vlr prepare`. Tags are `vX.Y.Z`.

## Release docs are written while working, not generated

- **Per change: fragments** (vl-release >= 0.7.0). Each PR adds `.release/notes.d/<issue>-<slug>.md` (user-facing
  Markdown; may start with one `## Section` heading to group under it) and `.release/changelog.d/<issue>-<slug>.md`
  (Debian-facing `- ` bullets). New files never conflict; editing the shared `_NEXT` files from parallel branches made
  every merge conflict every other open PR (2026-11-05). `vlr prepare` assembles them in file-name order after the
  `_NEXT` content and deletes them; `vlr finalize` keeps fragments merged after the cut.
- `.release/RELEASE_NOTES_NEXT.md`: line 1 `# <title>` (no version), set once per release; its body may be empty.
  `.release/CHANGELOG_NEXT.md`: only for edits to what is already staged there. `vlr prepare` renders the Debian
  stanza (urgency `high`, maintainer pinned in release.toml).
- Write them in the same change as the code; describe resulting behavior, not commits. Preview:
  `vlr prepare --dry-run`, `vlr release-title --staged`, `vlr release-body --staged`.
- `RELEASE_NOTES.md` and `debian/changelog` are written only by `vlr prepare` (in CI) and persisted only by
  `vlr finalize` after publication succeeded. `RELEASE_NOTES.md` does not exist until the first vl-release release.
- `vlr status` shows the phase: `pending` (staged docs for an unreleased VERSION), `prepared`, `released`.

## Cutting a release

```bash
vlr status                      # version, phase, staged-doc state, release title
vlr cut 1.8.0 --push            # explicit version (VERSION already 1.8.0, never released)
vlr cut patch|minor|major --push
```

`vlr cut` runs `release.toml` `test_command` (`bash tools/dev/verify.sh release packaging lifecycle shell`), bumps
(when given a part), commits `chore(release): vX.Y.Z`, tags, and with `--push` pushes `main` + the tag; the tag push
starts `release.yml`. Never without the maintainer's instruction: a `v*` tag publishes to the real APT repository.

## Building

`vlr build-deb` refuses an unprepared tree. It runs `[debian] pre_build` in the repo root
(`web/bin/build_release_payload.sh build/web-payload`: private icons via `web/bin/sync_private_icons.sh`,
`pnpm install --frozen-lockfile`, clean `pnpm build`, and the web tarball
`vaulthalla-web_<VERSION>_next-standalone.tar.gz`), copies the work tree to `build/deb/src` (minus `build_excludes`:
local secrets/overrides, stale build dirs, `.claude`), runs `dpkg-buildpackage -us -uc -b` there, and collects the
`.deb`, `.buildinfo`, `.changes` and the web tarball into `release/`. `vlr checksums` writes `release/SHA256SUMS`;
`vlr validate-artifacts` checks it plus the `[[debian.packages]]` contracts (one per built .deb: `vaulthalla`,
`vaulthalla-preview-cad`, `vaulthalla-preview-media`) (required/forbidden paths incl. the retired
`vaulthalla-cli.{socket,service}` (#110), `any_of` groups, the shipped `config.yaml` byte-identical to
`deploy/config/config.yaml`, prepared version, and the changelog in the package).

Local rehearsal of exactly that: `make deb` (`bin/install_deb.sh`): a throwaway worktree of **HEAD** → `vlr prepare`
→ `build-deb` → `checksums` → `validate-artifacts`, artifacts copied to `dist/`. Commit first; nothing is published.
The build needs the private icons (`$VAULTHALLA_WEB_ICON_SRC`, default `~/vaulthalla-web-icons`).

## GitHub workflows

- **Build modes (2026-10-04):** the PR gate compiles and runs the C++ suite at **-O0** (`buildtype=debug`, the meson
  default) with `-Werror`; release packages are the only **-O3** build (`debian/rules`: `optimization=3`,
  `-Dwerror=true`, `hardening=+all`, dpkg's `-O2` stripped, no LTO). A release never rebuilds or reruns the suite;
  `tools/dev/check_build_flags.py` checks the package's compile lines (-O3, hardening, -Werror, no diagnostics).
  1.8.x packages shipped -O0 and unhardened: a `cpp_args` default_option made meson drop dpkg-buildflags.
- `build_and_test.yml` (push/PR to main): three independent jobs that run side by side: `build` (on the heavy VM runners, label `ci-heavy`; `web` and `tooling` stay on `vps-ci`) (composite `runner`:
  core build at -O0 with -Werror → tests, `tools/dev/ci-test.sh` runs `vh_unit_tests` as 4 parallel gtest shards),
  `web` (typecheck, lint, build, budgets) and `tooling` (installs `vl-release`,
  `bash tools/dev/verify.sh release packaging lifecycle`, shellcheck, then the WebAuthn fuzz step: targets always
  build; the 60 s run happens on pushes to main and on PRs touching the parsers or build inputs). ccache works with the -O0 PCH only because
  `ci/Containerfile` sets `CCACHE_SLOPPINESS=pch_defines,time_macros,include_file_mtime,include_file_ctime`; without
  it every PCH compile is "uncacheable" and each run is a cold build (check `ccache -s` in the build log).
  - **Push gate (#185, 2026-10-10):** on pushes, a `gate` job (`ubuntu-latest`, seconds, `.github/scripts/ci_gate.py`)
    skips `build`/`tooling` when CI already tested the exact tree: a merged PR whose head has the pushed commit's tree
    and a `pull_request` run whose `build` job succeeded (i.e. the branch was up to date), or a `vlr cut` commit
    (`chore(release): vX.Y.Z`, the push's only commit, tagged `vX.Y.Z`) whose parent is covered and whose diff is
    purely the bump (only `release.toml`'s version files, every changed line old→new version). `vlr cut`'s resume paths
    push whatever is at HEAD (e.g. a release commit amended with code keeps its subject), hence the content check. A gated skip never
    counts as a passing build. Direct pushes always build; PRs always build; any gate error builds (fails open).
    `vlr finalize` commits carry `[skip ci]` (`release.toml` `finalize_commit_message`). Never add a skip marker to
    the cut commit: the tag points at it and GitHub would skip `release.yml`. Contract: `tools/contracts/test_ci_gate_contract.py`.
    `main`'s ruleset has no required status checks, so an untested PR merge simply gets the full push build.
- `release.yml` (tag `v*`, or `workflow_dispatch` with `ref` + `publish: dry-run|publish`):
  `release-check` (`vlr check --release --tag`, `vlr version check`) → `contracts-verify`, `web-verify` (typecheck/lint/colors
  only, no build), `docs-validate` → `release-artifacts` (`vlr prepare --record release/meta/prepare.json`, `build-deb`
  (its pre_build is the release's only web build), `pnpm --dir web budgets`, `check_build_flags.py release/build-deb.log`, `checksums`, `validate-artifacts`; uploads `release/`) → `publish-debian` → `github-release` →
  `finalize`; `docs-publish` needs only `docs-validate` + `publish-debian`.
  - Every downstream job re-runs `vlr prepare` (deterministic: dates come from the release commit) and downloads the
    artifact; `finalize` passes `--record` so it persists exactly what was built and published.
  - `publish-debian`: environment `Production`, concurrency `valkyrianlabs-apt-publish` (shared with every Valkyrian Labs publisher; queued, never cancelled),
    `vlr publish-deb --require-enabled` (idempotent: identical bytes skipped, different bytes refused, the APT index
    is verified by sha256). Credentials are step-scoped: `RELEASE_PUBLISH_MODE`, `NEXUS_APT_REPO` (falls back to the
    legacy `NEXUS_REPO_URL` variable), `NEXUS_USER`, `NEXUS_PASSWORD` (falls back to the legacy `NEXUS_PASS` secret).
    The repository is served by Apthalla (Valkyrian Labs' repository manager, which replaced Nexus on 2026-11-03). The
    `NEXUS_*` names and `RELEASE_PUBLISH_MODE=nexus` are vl-release's interface and the org's secret names, kept
    until they are renamed there; Apthalla takes the same logins.
  - `macos-package` → `macos-publish` (GitHub release assets, Homebrew casks) and `macos-publish-pkg` (VPS runner,
    environment `Production`, `CI_NETWORK=host`): `tools/macos/pkg/publish-pkg.sh` PUTs the `.pkg` and its `.sha256`
    to Apthalla's raw repository on the VPS loopback (`PKG_REPO_URL`, default
    `http://127.0.0.1:8090/repository/valkyrian-raw`, at `vaulthalla/<version>/`; `pkg.vaulthalla.sh` serves it) with
    `X-Checksum-SHA256`, same gate and credentials as the APT publication. Immutable: identical bytes skipped,
    different bytes refused (Apthalla answers 409), every upload read back. None of the macOS jobs gate the APT
    release. `macos.yml`'s manual `publish_test` / `upload_check` inputs rehearse the same path.
  - `github-release` (`contents: write`): `vlr github-release` creates/updates the release with the assets.
  - `finalize` (`contents: write`): `vlr finalize` commits the promoted `debian/changelog` + `RELEASE_NOTES.md` and the
    cleared `_NEXT` files onto `main` (a no-op if `main` already records the version). `main` has the ruleset
    "Core-Maintainer Only - Push Main" (pull request required; bypass: org admins and the repo admin role; checked
    2026-10-03), which rejects the plain workflow token. Finalize therefore needs GitHub Actions added as a bypass
    actor on that ruleset, or the secret `RELEASE_FINALIZE_TOKEN` (a bypass actor's token with contents:write, used
    by the job's checkout). Without either, everything is published and only `finalize` fails; fix, then re-run it.
  - `Production` environment: no protection rules (checked 2026-09-30); holds `NEXUS_USER`, `NEXUS_PASS`,
    `NEXUS_REPO_URL=https://apt.valkyrianlabs.com` (was apt.vaulthalla.sh until 2026-10-27; that host is now an
    alias of the same Apthalla repository), `RELEASE_PUBLISH_MODE=nexus`. Environment-scoped values are only
    visible to jobs that declare `environment: Production`.
- Composite actions (`.github/actions/`): `runner`, `build`, `test`, `setup_web`, `build_web`, `sync_web_icons`
  (calls `web/bin/sync_private_icons.sh`), `test_web`, `setup_valkyrianlabs_tools` (vl-release, pmdocs from apt).
  Heavy runners (2026-11-06): the compile-heavy `build` job runs on `vm-build-1..2` (label `ci-heavy`, VM `vl-gh-runner-home`;
  `CI_MEMORY=17g`, `CI_BUILD_JOBS=8`, 2 job slots). `runs-on` is `[self-hosted, Linux, X64, ${{ vars.CI_HEAVY_LABEL || 'ci-heavy' }}]`;
  failover: `gh variable set CI_HEAVY_LABEL --org valkyrianlabs --body vps-ci` (back to `ci-heavy` when the VM is up).
  Topology and install steps: valkyrianlabs/infra `docs/ci-runners.md`.
  Light runners: the Valkyrian Labs VPS build pool (valkyrianlabs org runners labelled `vps-ci`, in the shared `ci.slice`
  CPU/memory pool; the repository moved from vaulthalla/server in 2026-10). CI targets `[self-hosted, Linux, X64, vps-ci]`
  (fork PRs: `ubuntu-latest`, which has no icon store); release jobs target the same labels. Every step runs in the
  disposable CI container (`ci/run-ci`, rootless Podman, `ci/Containerfile` with the Build-Depends, g++ 14, ccache,
  Node/pnpm, vl-release, pmdocs, gh, shellcheck) as the job's default shell, composite actions included: no host
  sudo/apt/Docker, `sudo meson install` only touches the container. Caches persist on the runner in
  `~/.cache/vaulthalla-ci/{ccache,pnpm-store,npm}` of the runner user; the licensed icon store
  (`/opt/ci/vaulthalla-web-icons`) is mounted read-only (`CI_RO_MOUNTS`, `VAULTHALLA_WEB_ICON_SRC`).
  `setup_valkyrianlabs_tools` is no longer used by the workflows.

### Re-run rules

- A failed `publish-debian`/`github-release`/`finalize`/`docs-publish`: **Re-run failed jobs**. The artifact is
  reused, `publish-deb` and `github-release` skip what is already live with identical bytes.
- Never "Re-run all jobs" after `publish-debian` uploaded: a rebuild may produce different bytes, which publication
  refuses by design (exit 3). Cut a new patch version instead.
- Until `finalize` succeeds, `main` keeps the populated `_NEXT` files and the old history, so a failed release changes
  nothing and can be re-run.

## The lab is not part of the pipeline

vh-storage tests the **real** apt install/upgrade path: candidates are never installed there (see `/lab`).
`python3 -m tools.lab.lab_smoke --host vh-storage --apt-version X.Y.Z-1 [--from-version A.B.C-1] [--pg-restart]
[--reboot]` checks an upgrade from the real repository after publication, only when the maintainer asks; it mutates
the host. Evidence schema `vaulthalla.release.lab_smoke.v1`.

## Guardrail tests

`bash tools/dev/verify.sh release packaging lifecycle` (CI uses the same): `vlr check` + `vlr version check`;
`tools/contracts` (Debian install flow, rules, maintainer script safety/behavior, package layout, shipped migration
checksums, release workflow + `release.toml` contract, ws command map, no printf placeholders in core log calls), `tools/lab/tests`, `deploy/lifecycle/tests`, each with a
minimum test count (`run_suite` in verify.sh) so a suite dropped from discovery fails. Raise the floors when adding
tests.
